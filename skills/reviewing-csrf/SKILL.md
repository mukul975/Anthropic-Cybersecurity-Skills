# Analyzing CSRF Vulnerabilities

## When to Use

- When an application relies on **Cookies** to automatically authenticate requests. (Note: Endpoints relying strictly on `Authorization: Bearer <token>` headers are generally immune to standard CSRF, as browsers do not automatically attach custom headers to cross-origin requests).
- When evaluating endpoints that perform **state-changing operations** (POST, PUT, DELETE, PATCH).
- When evaluating GET endpoints that improperly perform state changes (e.g., `/api/deleteUser?id=123`).

**Do not use** CSRF PoCs to execute destructive actions (deleting data, changing passwords) against real users. Verify using non-destructive endpoints or dedicated test accounts.

## Prerequisites

- An interception proxy (Burp Suite, ZAP).
- Two separate browsers or browser profiles to simulate the victim and the attacker.
- Ability to host a simple HTML payload (e.g., via a local Python HTTP server or Burp's CSRF PoC Generator).

## Workflow

1. Initialize and execute the testing sequence.

```bash
# Verification block
echo test
```


### Step 1: Identify State-Changing Endpoints & Authentication
1. Find an endpoint that alters data (e.g., updating a profile, creating an API key, changing an email address).
2. Verify how the application authenticates the request. If it uses an `Authorization` header, CSRF is highly unlikely. If it uses a `Cookie`, proceed.

### Step 2: Identify CSRF Defenses
Examine the request and response for standard CSRF protections:
- **Anti-CSRF Tokens**: Look for hidden form fields (e.g., `csrf_token`, `__RequestVerificationToken`) or custom headers (e.g., `X-CSRF-Token`).
- **SameSite Cookies**: Inspect the `Set-Cookie` header during login. Is it `SameSite=Strict`, `SameSite=Lax`, or `SameSite=None`?
- **Referer / Origin Checks**: Does the server inspect the `Referer` or `Origin` HTTP headers to ensure the request originated from its own domain?

### Step 3: Bypass Testing
Systematically attempt to bypass the identified defenses:
- **Token Bypasses**: 
  - Remove the token entirely.
  - Submit an empty token.
  - Substitute the token with one generated by a different user account.
  - If the application expects a POST request, change the method to GET and see if the token check is skipped.
- **Referer/Origin Bypasses**:
  - Remove the `Referer` header entirely (using `<meta name="referrer" content="no-referrer">` in your PoC).
  - Spoof the Referer if the check is weak (e.g., if it checks if `target.com` is *anywhere* in the string, use `http://attacker.com/target.com.html`).
- **SameSite=Lax Bypasses**:
  - `Lax` prevents POST requests from carrying cookies cross-origin, but allows top-level GET requests. If a state change can be triggered via GET, `Lax` is bypassed.

### Step 4: Construct and Execute PoC
1. Create an HTML file on an attacker-controlled domain.
2. For POST requests, create a form that auto-submits:
   ```html
   <form action="https://target.com/api/updateEmail" method="POST">
     <input type="hidden" name="email" value="hacked@attacker.com">
   </form>
   <script>document.forms[0].submit();</script>
   ```
3. For GET requests, use a simple image tag:
   ```html
   <img src="https://target.com/api/deleteAccount">
   ```
4. While logged into the target application as the victim, open the attacker HTML file in the same browser. Check if the state change occurred.
## Key Concepts

| Term | Definition |
|------|------------|
| **CSRF (Cross-Site Request Forgery)** | An attack that forces an end user to execute unwanted actions on a web application in which they're currently authenticated. |
| **SameSite Cookie Attribute** | A browser security feature that determines whether cookies are sent with cross-site requests. `Strict` sends cookies only for first-party requests. `Lax` sends cookies for top-level navigations (like following a link). `None` sends cookies with all requests. |
| **Synchronizer Token Pattern** | The primary defense against CSRF. The server generates a unique, cryptographically strong, and unpredictable token per session, requiring it to be submitted with every state-changing request. |

## Common Scenarios

### Scenario: False Positive - Custom Headers
**Context**: You find a POST request with no CSRF token. You assume it's vulnerable.
**Analysis**: You notice the request requires a custom header: `X-Requested-With: XMLHttpRequest` or `Content-Type: application/json`.
**Action**: Standard HTML forms cannot issue requests with custom headers or `application/json` Content-Types without utilizing JavaScript (Fetch/XHR). Browsers enforce CORS (Cross-Origin Resource Sharing) on these requests, issuing a Preflight `OPTIONS` request. If the server does not explicitly allow the attacker's origin via CORS, the browser will block the request. The application is likely secure against standard CSRF.

### Scenario: False Negative - GET Request Side-Effects
**Context**: The developer secured all POST/PUT/DELETE requests with strict CSRF tokens.
**Analysis**: The application features a "One-Click Unsubscribe" link sent in emails, which maps to `GET /api/unsubscribe`. 
**Action**: Because it is a GET request, an attacker can embed `<img src="https://target.com/api/unsubscribe">` on a malicious forum. When the victim views the forum, the browser fetches the image, automatically attaching the victim's session cookies, triggering the unsubscription.
